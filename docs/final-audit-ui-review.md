# Повторный независимый аудит бизнес-команд и эксплуатации

Дата: 11 ноября 2026 года. Проверка выполнена после исправлений основного аудита.
Этот документ дополняет общий отчёт; нагрузочные измерения и восстановление
резервных копий описываются отдельными протоколами.

## Область и метод

Повторно прочитаны `feedback/services.py`, календарь `feedback/sla.py`, модель
доступа, worker, настройки Django, профиль production, nginx и bootstrap ролей БД.
Проверены порядок блокировок, границы транзакций, повтор уведомления, защита
внутренних событий и поведение при недоступности исполнителя.

Семь самостоятельных проверок выполнены в создаваемой Django тестовой БД
`test_modus_final_ui_review` на PostgreSQL 17. После запуска эта БД удалена
тестовым runner. Основная БД и БД нагрузочного испытания не использовались.
Проверка передачи proxy-заголовков выполнена на установленном Waitress 3.0.2
и настоящем Django SecurityMiddleware. Проверка отклонения пароля-заглушки
использовала mock соединения; реальные роли и пароли не менялись.

## Подтверждённые свойства

| Сценарий | Наблюдение |
|---|---|
| Ошибка сохранения события после начала команды | Изменение карточки, комментарий и outbox откатываются одной транзакцией |
| Два worker одновременно выбирают одну доставку | Создано одно Notification; суммарно одна успешная доставка |
| Повтор failed-доставки с уже существующим Notification | Сохраняется одна идентичность уведомления, доставка завершается sent |
| Автор обращается к команде повторной доставки | Доступ запрещён, состояние доставки не меняется |
| NO_RESPONSE без фактической доставки напоминания | Закрытие отклоняется даже после истечения первоначального срока |
| Одновременные связи A→B и B→A | Сохраняется одна связь; противоположная отклоняется без цикла |
| Повторное открытие при отсутствии доступных сотрудников очереди | После исправления создаётся REVIEW без исполнителя; автор не теряет возможность пересмотра |

Порядок основных блокировок согласован: карточка перед уточнением или доставкой;
изменения графа дубликатов дополнительно сериализуются advisory lock. Параллельные
пробы подтверждают проверенные случаи, а не отсутствие всех возможных конфликтов.

Для внутренних уведомлений доступ проверяется при постановке, доставке и чтении.
Авторство исключает доступ к внутреннему содержимому даже при дополнительной
операционной роли. Доставка сама по себе не создаёт постоянного права читать событие.

## Найденное при повторной проверке и закрытие

### P1: HTTPS-цикл перенаправлений на входе

В первоначальном production-профиле Waitress запускался без доверенного proxy.
Его стандартная настройка удаляла `X-Forwarded-Proto` до Django. Воспроизведён
ответ 301 с Location, равным исходному HTTPS URL `/accounts/login/`; проверка
`/health/` этого не выявляла, поскольку health освобождён от перенаправления.

Профиль исправлен: явно заданы `--trusted-proxy=*` и доверие только
`x-forwarded-proto`. Контрольная middleware-проба возвращает 200 и HTTPS scheme.
Доверие допустимо в предусмотренной закрытой сети: порт web не опубликован,
nginx перезаписывает заголовок. При изменении сетевой схемы нужно заново проверить
эту границу доверия. Отдельная TLS-проверка входа включена в итоговую приёмку.

### P2: начальный пароль владельца БД

Bootstrap проверял runtime-пароль, но пропускал образец `CHANGE_ME` в пароле owner.
Это подтверждено с mock соединения. Добавлена отдельная проверка owner-пароля
при DEBUG=0; повторная проба подтверждает отказ до попытки соединения с БД.

### P2: повторное открытие без доступного исполнителя

Первый прогон получил `assignee_ineligible`, HTTP 422: закрытая карточка зависела
от восстановления персонала старой очереди. Команда изменена: создаёт новый цикл
REVIEW без исполнителя и сохраняет причину переназначения. Повторный независимый
прогон подтвердил это поведение. Одобрение и возобновление реализации продолжают
требовать допустимого исполнителя.

### P2: объём истории одной карточки

Ранее `_detail` загружал все события, решения и циклы; затем повторно обходил
события для каждого цикла. Размер ответа и память росли с полной историей карточки.
Это отдельная проблема от общего числа карточек в системе.

Внесены пределы серверных страниц:

- обсуждение — 50 сообщений;
- события — 50;
- циклы — 10;
- завершённые уточнения — 25;
- блок решения — текущий цикл; прежние решения доступны в соответствующих циклах.

Подтверждения IMPLEMENT выбираются только для видимых циклов, по одному последнему
событию на цикл. Внутренние события отфильтровываются до формирования страниц.
Переход между страницами сохраняет параметры остальных разделов. После 409
сохраняются текущие страницы, текст внутреннего черновика и его видимость.

Регрессии используют карточку с 55 публичными комментариями, дополнительными
внутренними строками, более 50 событиями, 12 циклами и 30 завершёнными уточнениями.
Последние страницы доступны, внутренние строки автору не раскрываются.

### Дополнительные уточнения аналитики и справочников

Будущая дата среза теперь отклоняется с 422. Историческая аналитика PostgreSQL и
SQLite сохраняет отсутствие исполнителя и флаги нарушения сроков: JSON null и
JSON true больше не искажаются при приведении типов SQLite.

Некорректный старый `extra_roles` не повышает права и не вызывает 500. SQL-предикат
списка исполнителей допускает дополнительные роли только в корректном массиве
известных строк; полный справочник сотрудников не переносится для этой проверки
в Python. Новые записи дополнительно проверяются `User.clean`.

- HTTP/UI-регрессии и прежние проверки интерфейса: **39 из 39 PostgreSQL**,

- Ранее выполненный браузерный прогон: **9 основных и 4 дополнительных сценария**,

пробы и JSON-наблюдения сохранены в игнорируемой `.local/`.

## Практические границы вывода

В проверенной области после перечисленных исправлений незакрытых P1 не выявлено.
Это не доказывает доступность за месяц, выполнение RPO/RTO во всей инфраструктуре
или производительность на миллионе карточек и десяти миллионах событий.
Окончательный вывод по нагрузке требует соответствующего итогового протокола.

Для исключительно длинных историй следующий шаг — keyset-переходы по sequence
и паре created_at/id вместо глубокого OFFSET, с замером SQL-планов на таких
карточках. Сейчас объём загружаемых строк ограничен страницей, но стоимость
очень далёких страниц отдельно не аттестована.

Текущая доставка — запись внутри приложения с уникальным Notification/outbox.
При добавлении внешней почты или других необратимых каналов понадобятся отдельная
идемпотентность провайдера и fencing повторно захваченной lease. Проверка одной
внутренней записи не является гарантией однократной внешней отправки.

## Закрытие замечания о proxy logs

Основной исполнитель добавил safe access log без query string и ограничил
стандартный error log критическими ошибками процесса. `production_probe.py`
проверяет настоящий HTTPS-запрос с уникальным canary в q и отсутствие этого
значения в журналах прокси. Итоговый набор из 7 production-проверок пройден.
Замечание о логировании поискового текста закрыто в описанном контуре.
