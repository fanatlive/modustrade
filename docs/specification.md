# Техническая спецификация системы обратной связи

## Назначение и статус документа

Спецификация закрепляет вариант работающего MVP по переработанному ТЗ из отчёта.
Исходный документ компании является хакатонным брифом и допускает другие форматы
участия. Промышленные параметры ниже являются предлагаемыми требованиями для
последующего пилота. Их достижение должно подтверждаться проверками.

Цель — регистрировать проблемы, предложения и положительные отзывы сотрудников,
назначать ответственность, сохранять ход рассмотрения и проверяемый результат.
Обращение не должно теряться из-за отсутствия маршрута или сбоя уведомления.

Исходные материалы: ТЗ хакатона ГК «Модус Трейд» и документ с 20 синтетическими
обращениями. Тексты карточек являются данными, а не требованиями создать
упомянутые в них каталоги, проектные системы или планировщики.

## Объём

MVP включает учётные записи, роли и область доступа, создание карточек,
категории/приоритеты, маршрутизацию, резервные очереди, обработку, уточнения,
комментарии, решения, подтверждение результата, повторное открытие, историю,
уведомления в приложении, поиск, фильтры, пагинацию, аналитику и импорт демо.

В текущую реализацию не входят вложения, SSO, анонимность, внешние клиенты,
опросы и реальные интеграции. Эти ограничения показываются в документации.
Работающее поведение, имитация и планы не должны смешиваться при демонстрации.

## Архитектура

Модульный монолит Django, PostgreSQL, серверные шаблоны и отдельный worker.
Модули: пользователи и права, обращения, маршруты, решения, сроки, история,
уведомления, аналитика и импорт. Локально допускается SQLite с ограничениями.

Изменение состояния, событие истории и outbox сохраняются одной транзакцией.
Доставка начинается после фиксации. Внешний сервис не является условием
успешной регистрации. API изменения получает ожидаемую версию карточки;
устаревшая версия возвращает конфликт. Создание идемпотентно в рамках ключа
и содержимого команды; повтор ключа с другим телом отклоняется.

Фоновое задание имеет время владения, повтор с увеличением задержки,
ограничение попыток и видимую очередь ошибок. Перед доставкой проверяется
актуальный доступ получателя. Событие и получатель уникализируют доставку.

## Модель данных

| Сущность | Содержание |
| --- | --- |
| User, OrgUnit | Пользователь, роли, подразделение, допуск |
| Category, Queue | Категории и ответственные очереди |
| RoutingRule | Условия, приоритет, версия и цель маршрутизации |
| Ticket | Тип, текст, автор, категории, приоритеты, конфиденциальность, очередь, исполнитель, состояние и текущий результат |
| ProcessingCycle | Отдельный цикл обработки, сроки, ответ, решение и завершение |
| Decision | Автор, код, обоснование и критерий результата |
| InfoRequest | Вопрос, срок, состояние возврата и ответ |
| Comment | Сообщение автору или внутренняя заметка |
| Event | Последовательная история с происхождением события |
| Outbox, Notification | Фоновая доставка и уведомление получателя |
| ImportBatch, ImportRecord | Источник, контрольная сумма, исходные строки и проблемы |
| TicketRelation | Связь дубликата с основной карточкой |
| IdempotencyRecord | Ключ команды, хеш и созданная карточка |

Ключ карточки — UUID, пользовательский номер уникален. Источник имеет собственный
идентификатор. Внешние ключи защищают связи; исторические справочники не удаляются
каскадно. Запрещены самоссылка и циклы дубликатов. Закрытие требует кода,
описания результата и даты закрытия. События имеют уникальную последовательность.

Подразделение автора не подменяет подразделение, к которому относится обращение.
Условная роль из исходника не является идентификатором сотрудника.

Индексы нужны для автора и даты, очереди/исполнителя и состояния, категории,
последовательности событий и состояния фонового задания. Полнотекстовый поиск
и поиск похожих формулировок могут расширяться после проверки нагрузки и качества.
Совпадение темы не является основанием автоматически объединить обращения.

## Доступ

Автор читает свои карточки и публичные сообщения. Исполнитель обрабатывает
назначенные карточки и разрешённые очереди. Координатор отвечает за разбор и
передачу. Руководитель ограничен согласованным контуром. Администратор настройки
не получает автоматически доступ к содержимому всей компании.

STANDARD доступно по обычным объектным полномочиям. RESTRICTED требует отдельного
допуска и соответствующей очереди; автор сохраняет доступ к собственной карточке.
Авторство само по себе не даёт права выполнять команды обработчика.

Проверки выполняются на сервере для карточки, списка, поиска, истории,
уведомлений и аналитики. Внутренние сообщения не передаются автору ни одним каналом.
Ссылка дубликата не раскрывает недоступную основную карточку.

## Регистрация и маршрутизация

Обязательны тип, категория и описание. Предполагаемое решение и затронутое
подразделение необязательны. Описание — 10–10000 символов, предлагаемое решение —
до 5000. Автор определяется из сеанса. После фиксации возвращаются номер и карточка.

Маршрутизация учитывает конфиденциальность, категорию, тип и затронутое подразделение.
Выбирается действующее правило высшего приоритета. Неоднозначность, отсутствие
правила или допустимого исполнителя приводят к контролируемому разбору.
Ответственная очередь обязательна; исполнитель может отсутствовать до разбора.

Деактивированный сотрудник не получает новые назначения. Открытые обращения
должны быть переданы действующему ответственному. Переназначение не обнуляет сроки.

## Состояния и решения

Состояния: NEW, REVIEW, WAITING_INFO, IN_PROGRESS, CLOSED.
Решения: APPROVED, DECLINED, ACKNOWLEDGED.
Итоги: IMPLEMENTED, DECLINED, ACKNOWLEDGED, DUPLICATE, WITHDRAWN, NO_RESPONSE.

| Переход | Условие |
| --- | --- |
| Создание → NEW | Данные сохранены, назначена очередь |
| NEW → REVIEW | Действующий исполнитель начинает разбор |
| REVIEW → IN_PROGRESS | Одобрение, критерий, исполнитель и плановый срок |
| REVIEW/IN_PROGRESS → WAITING_INFO | Конкретный вопрос, адресат, срок и состояние возврата |
| WAITING_INFO → предыдущее | Ответ или контролируемое продолжение |
| REVIEW → CLOSED | Отказ с причиной, обработанный отзыв или подтверждённый дубликат |
| IN_PROGRESS → CLOSED | Достигнут критерий, описан результат и подтверждение |
| Активное → CLOSED/WITHDRAWN | Явный отзыв; остановка начатой работы согласуется отдельно |
| CLOSED → REVIEW | Обоснованное повторное открытие и новый цикл |

Прямое присваивание состояния через пользовательский запрос не допускается.
Каждая команда проверяет полномочия, состояние, обязательные поля и версию.
Одобрение не считается реализацией. Положительный отзыв не увеличивает число
реализованных улучшений. Отказ без причины и реализация без результата запрещены.

Повторное открытие автором возможно в пределах пяти рабочих дней. После этого
его выполняет координатор с причиной. Предыдущие результаты и просрочки сохраняются.

## Уточнения и сроки

Одновременно активен один запрос уточнения. Сохраняются вопрос, срок, состояние
возврата, ответ и время. Внутренняя заметка не заменяет ответ автора.
Ожидание другого подразделения не называется отсутствием ответа автора.

Предлагаемые сроки: высокий — 4 рабочих часа до ответа и 3 рабочих дня до решения;
средний — 1/10 дней; низкий — 2/20 дней. Рабочий день содержит 8 часов.
Срок выполнения одобренного предложения устанавливается отдельно.

Первый ответ — содержательная реакция обработчика, доступная автору, включая
содержательный вопрос. Автоматическое подтверждение, назначение и внутренняя
заметка не считаются ответом. Первое время реакции не приостанавливается.

Пауза рассмотрения допускается только при ожидании автора и ограничена пятью
рабочими днями. Истечение ведёт к напоминанию/эскалации; координатор выбирает
продолжение, обоснованное продление или NO_RESPONSE. Молчание не означает отказ.
Пауза после одобрения не переносит срок реализации автоматически.

Календарь и его версия сохраняются с циклом. Демонстрационный календарь
Asia/Bishkek, будни 09–13 и 14–18 без праздников должен быть заменён утверждённым
календарём компании до пилота.

## Аналитика

Показываются распределения по типам/категориям/состояниям/приоритетам, открытые
карточки, просрочки, отсутствие исполнителя или ответа, решения и результаты.

Доля закрытых вычисляется по выбранной когорте на дату среза. Рассмотренные —
с содержательным решением. Реализованные — с подтверждённым IMPLEMENTED.
Время первого ответа рассчитывается только при известных исходных отметках;
рядом указываются размер выборки и число ещё не получивших ответа.
Отсутствие данных отображается явно. В промышленном расчёте демо исключается
из числителя и знаменателя. Отдельно показывается охват пригодных данных.

## Преобразование исходного набора

Все 20 записей имеют по девять непустых полей и уникальные A-001…A-020. Типы:
9 проблем, 10 предложений, 1 положительный отзыв. Приоритеты: 4 высоких,
9 средних, 7 низких. Категорий 18. Даты подачи отсутствуют во всех карточках.

Конвейер: исходный документ и SHA-256 → неизменяемые записи → проверка структуры
и словарей → явное отображение → рабочие демонстрационные карточки.
Повтор не создаёт копии и не перезаписывает работу пользователя. Новая версия
источника с отличающимся содержимым создаёт конфликт для проверки.

Исходный статус и пример действия сохраняются отдельно. A-004/A-018 требуют
проверки результата. Все добавленные даты, пользователи, маршруты, вопросы и
исходы помечаются синтетическими. Время импорта не является временем подачи.
Подробные решения отображения приведены в decisions.md.

## Ошибки и сбои

- Нет маршрута: резервная очередь соответствующего допуска.
- Старая версия: конфликт без изменения карточки.
- Повтор создания: прежняя карточка по ключу.
- Невалидные поля: понятная ошибка и сохранённый введённый текст.
- Недоступна БД: успешная регистрация не показывается.
- Сбой уведомления: бизнес-операция сохранена, доставка повторяется.
- Утрачен доступ получателя: уведомление с содержимым не выдаётся.
- Неизвестный справочник импорта: диагностическая ошибка без угадывания.
- Дубликат: обязательная основная карточка, запрет самоссылки и циклов.
- Изменившийся источник: исходная и рабочая версии не смешиваются молча.

## Предлагаемые нефункциональные требования пилота

| Требование | Целевое значение |
| --- | --- |
| Пользователи / активные сессии | 5000 / 100 |
| Карточки / события | 1 млн / 10 млн |
| Нагрузка | 20 запросов/с, 30 минут; 70% просмотр, 20% поиск, 10% изменения |
| p95 просмотр / изменение / поиск | 1 / 1,5 / 2 секунды |
| Технические ошибки | ≤0,5% при проверочной нагрузке |
| Доступность | 99,5% за месяц с плановыми остановками |
| RPO / RTO | ≤15 минут / ≤2 часов |

Стенд и протокол должны описывать CPU/RAM/SSD, данные, сеть, кэш, размеры ответов
и загрузку файлов при их появлении. Эти значения не подтверждены фактом
существования MVP. Резервирование охватывает БД, историю, outbox и файлы при
их добавлении. Требуется фактическое восстановление и сверка связности.

До реальных данных обязательны HTTPS, CSRF/XSS-защита, серверная авторизация,
ограничение частоты операций, защита секретов, отключение debug, журналирование
изменений полномочий и решений, отсутствие чувствительных текстов в техлогах,
утверждённое хранение и удаление. Юрисдикцию и правовой режим исходники не задают.

## Приёмка

Проверяются сквозная регистрация и результат; резервный маршрут; запрос/ответ;
обоснованный отказ; подтверждённая реализация; отзыв и повторное открытие;
защита чужих карточек, внутренних заметок и конфиденциального контура;
идемпотентное создание и импорт; конфликт версий; сохранение при сбое уведомления;
сохранение всех исходных строк; маркировка A-004/A-018; отсутствие ложных нулей
в метриках и воспроизводимый локальный запуск.

Для пилота дополнительно нужны испытания PostgreSQL при конкуренции,
утверждение полномочий и SLA, мониторинг, проверка восстановления, безопасные
файлы при включении и эксплуатационные регламенты. Невыполненные пункты
фиксируются как ограничения, а не заявляются реализованными.
