# Воспроизводимая нагрузочная проверка

`scripts/load_check.py` измеряет реальные HTTP-запросы к отдельному процессу
Waitress с восемью потоками, Django и PostgreSQL. Проверка создаёт только новую
синтетическую БД вида `modus_<идентификатор>_load`. Существующая БД любого
содержимого не изменяется; имя `modus` и любые имена вне этого шаблона запрещены.
Основное приложение на порту 8000 продолжает работать отдельно.

## Запуск

Нужны зависимости проекта, запущенный PostgreSQL, учётная запись владельца с
`CREATEDB` и свободный порт 8767. В локальном Compose PostgreSQL доступен на
127.0.0.1:55432. Runtime-роль приложения намеренно не имеет `CREATEDB`.

```powershell
$env:POSTGRES_PORT='55432'
.venv/Scripts/python.exe scripts/load_check.py --database modus_bounded_20261111_load --cards 10000 --events 100000 --rps 20 --duration 1800 --sessions 100 --report .local/load/bounded-30min.json
```

Для короткой проверки используйте `--duration 60`; значения по умолчанию —
10 тыс. карточек, 100 тыс. событий, 20 запросов/с, 100 сессий и 60 секунд.
Для полного целевого объёма задаются `--cards 1000000 --events 10000000`.
Перед созданием БД проверяется свободное место: консервативная оценка
12 КиБ/карточку + 4 КиБ/событие + 1 ГиБ резерва. При дефиците команда сохраняет
JSON с отказом и `database_created=false`, не создавая БД. Оценка является
защитным ограничением, а не измеренным размером производственных данных.

## Методика и границы

Используется открытый поток запросов с заданной частотой. Каждые десять запросов
содержат семь просмотров, два поиска и один комментарий; порядок воспроизводимо
перемешивается. Просмотр включает карточку с полной историей и список; поиск
использует два русских термина через действительный scoped full-text поиск.
Идентификаторы просмотров выбираются из всего подготовленного набора.
Изменение выполняет настоящий POST комментария с CSRF, проверкой полномочий
и версии. HTTP 302 после сохранения — успешный ответ записи; переход вслед за
ним не добавляет скрытый второй запрос к нагрузке.

Создаются 100 независимых авторизованных сессий десяти исполнителей общей
очереди. Учётные записи не имеют пригодных паролей; сессии создаются внутри
исключительно тестовой БД до измерения. Производительность входа и подбор
паролей проверяются отдельно. Для каждой сессии выделена собственная карточка
изменений, чтобы генератор сам не создавал искусственные конфликты версии.

Показатели включают задержку от планового времени отправки до полного ответа,
включая ожидание очереди. При исчерпании 100 доступных клиентов запрос считается
пропущенным и входит в долю ошибок. HTTP 4xx, 5xx и сетевые ошибки также входят
в долю ошибок; конфликты и ограничение частоты не скрываются. Отчёт содержит
p50/p95/p99/max по операциям, статусы, фактический поток, пропуски и объём ответов.
Перед измерением сохраняется действительный `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`
запроса поиска от имени исполнителя с теми же объектными ограничениями.

Контрольные пороги: p95 просмотра ≤1000 мс, изменения ≤1500 мс, поиска ≤2000 мс;
ошибки ≤0,5%. `full_scale_target_verified` становится true только при полном
объёме 1 млн/10 млн, 100 сессиях, ≥20 запросах/с, ≥30 мин и соблюдении порогов.
Проверка меньшего набора подтверждает исключительно параметры этого набора.

Синтетическая структура упрощена: двадцать категорий, одна очередь,
примерно четверть закрытых карточек, равномерное число коротких событий,
один цикл и тексты заданного размера. Это не проверка всех распределений
компании, нескольких циклов с тяжёлыми JSON, вложений или внешних интеграций.
Подготовка и `ANALYZE` прогревают часть страниц; отдельное испытание холодного
кэша не выполняется. Счётчик `limits_met` относится к указанной HTTP-смеси.
Аналитика, вход и throughput фонового обработчика в эту смесь не входят;
для них необходимы отдельные проверки. Worker в тестовой БД не запускается:
outbox сохраняется действительными транзакциями, но доставка не замеряется.

Для повторения фиксируйте CPU/RAM/SSD, ограничения Docker и фоновые нагрузки.
JSON содержит версию ОС/Python, число логических CPU, свободный диск,
размер подготовленной БД и продолжительность. Параллельная компиляция,
другие тесты и приложения могут влиять на результаты.

## Завершение

Каждые 30 секунд атомарно сохраняется промежуточный JSON с фактически прошедшим
временем, счётчиками и предварительным p95 (`results_provisional=true`).
По умолчанию после 60 секунд генерация прекращается, если наблюдаемая доля
ошибок и пропусков превышает 0,5%; после завершения уже отправленных запросов
сохраняется итог с `phase=aborted`, причиной и фактическими измерениями.
`--fail-fast-after 0` отключает этот контроль для специального исследования.

Для управляемой остановки создайте файл из поля `stop_file` отчёта; по умолчанию
это имя отчёта с расширением `.stop`. Например:

```powershell
New-Item -ItemType File -Path .local/load/bounded-30min.stop
```

Путь можно явно задать `--stop-file`, но только внутри `.local/load/`.
Существующий stop-файл блокирует новый запуск до создания БД. Прерванный запуск
всегда имеет `limits_met=false`; он не считается выдержавшим заданную длительность.

В `finally` завершается только созданный процесс Waitress, закрываются свои
соединения и удаляется только БД, отсутствовавшая до начала этого запуска.
Отчёт и журнал остаются в игнорируемой `.local/load/`.
`--keep-database` сохраняет созданную синтетическую БД для исследования;
это явно указывается в JSON, и оператор должен удалить её после анализа.
Скрипт не удаляет контейнеры, тома и посторонние базы данных.
