# Эксплуатация и восстановление

Локальный `compose.yaml` остаётся демонстрационным. `compose.production.yaml`
содержит отдельный профиль с DEBUG=0/DEMO_MODE=0, TLS-прокси, непубличной БД,
отдельным процессом миграций и DML-ролью приложения. Оба профиля привязаны к
loopback; открытие корпоративной сети требует настройки инфраструктуры владельцем.

## Запуск профиля с TLS

1. Скопировать `.env.production.example` в игнорируемый `.env.production`.
2. Сгенерировать независимые SECRET_KEY (не менее 50 символов), пароли owner/runtime
   (не менее 24 символов для runtime) и OPERATIONS_TOKEN (не менее 32 символов).
   Примеры `CHANGE_ME` не являются секретами и отвергаются приложением.
3. Указать реальные ALLOWED_HOSTS, HTTPS origin, BUSINESS_TIMEZONE и каталог
   сертификата `server.crt`/ключа `server.key`. Ключ и env не добавлять в Git.
4. Последовательно собрать два образа и запустить:

```powershell
docker compose --env-file .env.production -f compose.production.yaml build migrate
docker compose --env-file .env.production -f compose.production.yaml build backup
docker compose --env-file .env.production -f compose.production.yaml up -d
docker compose --env-file .env.production -f compose.production.yaml run --rm migrate python manage.py check --deploy
docker compose --env-file .env.production -f compose.production.yaml run --rm migrate python manage.py createsuperuser
```

Начальных паролей/демо-пользователей в этом профиле нет. Администратор создаёт
реальные учётные записи и утверждает роли. После создания координатора с допуском:

```powershell
docker compose --env-file .env.production -f compose.production.yaml run --rm migrate python manage.py bootstrap_initial --coordinator LOGIN --dry-run
docker compose --env-file .env.production -f compose.production.yaml run --rm migrate python manage.py bootstrap_initial --coordinator LOGIN
```

Команда создаёт две резервные очереди и категорию «Не знаю», без синтетических
карточек. Настроенные очереди не перезаписываются. Категории/маршруты далее
настраиваются через admin; изменение маршрута создаёт новую версию.

TRUST_PROXY=1 допустим только в закрытой сети, где приложение доступно через
контролируемый nginx. Waitress явно доверяет только x-forwarded-proto из этой
сети. Nginx перезаписывает X-Forwarded-Proto и X-Real-IP; клиентские
значения не передаются. Порт web в production не опубликован. TLS-проба на этом
компьютере использует временный self-signed сертификат, который не установлен в
доверенные хранилища. Для рабочего домена нужен действующий сертификат.

## Диагностика

- `/health/`: БД доступна, 200; при ошибке БД 503. Проверка не перенаправляется на TLS.
- `/health/worker/`: последний успешный проход не старше 120 секунд и без ошибки;
  иначе 503. Клиент получает только статус. Container readiness использует Host
  из первого ALLOWED_HOSTS, поэтому рабочий домен не требует добавления loopback.
- `/operations/metrics/`: JSON агрегатов, только с `Authorization: Bearer TOKEN`.
  Тексты обращений и идентификаторы пользователей в ответ не включаются.
- `python manage.py operations_status --fail-on-alert`: ненулевой exit при просроченном
  heartbeat, failed outbox или возрасте ожидающего события свыше 120 секунд,
  включая задания в backoff. Просрочка next_attempt показана отдельно.
- `/deliveries/failed/`: доступная координатору очередь неудачных доставок с мотивированным
  повтором. Область очередей и конфиденциальность проверяются при чтении и повторе.
- `docker compose ps`, журналы worker/web/backup; в production включена ротация 3×10 МБ.

Nginx access log содержит метод, URI без query, статус, размер и длительность.
Поисковый `q` и токены не записываются. Error log прокси ограничен критическими
ошибками процесса: стандартный формат подробных upstream-ошибок включает
первоначальный query. Ответы 4xx/5xx контролируются по безопасному access log.

Внешний мониторинг должен опрашивать readiness и авторизованные метрики каждые
30 секунд, уведомлять дежурного при двух неуспехах подряд и проверять сертификат,
диск, возраст резервной копии. Контакт дежурного и внешний канал определяет владелец;
приложение не отправляет сообщения в неуказанные каналы.

## Резервирование

`ops/backup.py` получает repeatable-read snapshot, контрольные подписи таблиц и
`pg_dump -Fc --snapshot` из одного среза. SHA-256 архива и подписи находятся в
соседнем JSON. Политика локального профиля: каждые 600 секунд, до 14 дней/2016
копий/1 ГБ, с сохранением последней. Ограничение по объёму может сократить глубину
истории; возраст последней копии контролируется отдельно. При недостатке свободного
места новая копия отклоняется, имеющиеся не удаляются для освобождения места.
Свежесть считается от начала snapshot, а не завершения дампа. Health проверяет
наличие архива, согласованность manifest и размер; криптографическая проверка
содержимого выполняется при retention и restore-verify. Повреждённые/неполные
пары не вытесняют последнюю проверенную полную копию.

```powershell
.\.venv\Scripts\python.exe ops/backup.py create
.\.venv\Scripts\python.exe ops/backup.py restore-verify --archive .local/backups/ИМЯ.dump
docker compose --profile operations build backup
docker compose --profile operations up -d backup
```

Production включает backup автоматически. Каталог BACKUP_DIR должен находиться на
защищённом хранилище, иметь ограниченный ACL и отдельную копию вне хоста. Архив
содержит данные и хэши паролей; SHA-256 проверяет целостность, а не шифрует его.
Шифрование диска и доставка в защищённое внешнее хранилище — настройки размещения.
Резервирование на одном компьютере не защищает от потери компьютера.

Вложения хранятся в томе `production_attachments` (`/app/media/attachments`), а не в БД,
поэтому `ops/backup.py` их не включает. Для пилота добавьте копирование этого тома
по тому же расписанию; восстановление без него оставит карточки без файлов.

`restore-verify` проверяет SHA-256, создаёт только новую базу `modus_verify_UUID`,
восстанавливает, сравнивает число/контрольные подписи строк всех таблиц и проверяет
валидацию constraints. Затем удаляет только эту созданную базу. Существующая рабочая
БД никогда не является целью этой команды. Подписи требуют PostgreSQL того же
major (17); перенос версии проверяется отдельным сценарием обновления.

При аварии: остановить запись и worker, сохранить повреждённый том, выбрать
проверенный архив, выполнить restore-verify, затем восстановить в НОВУЮ рабочую
БД, выполнить migrate и `ops/bootstrap_db.py` от владельца схемы (восстановление
с --no-acl не переносит DML-grants), check и проверку данных, переключить POSTGRES_DB, запустить
web/worker и проверить outbox. Не восстанавливать поверх работающей БД. RTO включает
обнаружение, предоставление хоста, переключение и приёмку; время локального
restore-verify само по себе не доказывает RTO всего сервиса.

Проверять восстановление не реже месяца и перед миграциями. Полный pg_dump каждые
10 минут пригоден для малого пилота; на целевом объёме требуется замер длительности
и объёма. При выходе за интервал — PostgreSQL base backup + непрерывный WAL/PITR
на отдельном хранилище с повторным испытанием RPO/RTO. Эти инфраструктурные
гарантии не заявляются по результатам маленького локального стенда.

## Блокировка и хранение данных

После блокировки/снятия роли/допуска или смены очереди проверить:

```powershell
python manage.py reconcile_assignments --actor coordinator
python manage.py reconcile_assignments --actor coordinator --apply
```

Сначала выводится план в области координатора; каждое применение использует
обычную транзакционную команду назначения и создаёт историю. Если допустимого
исполнителя нет, карточка остаётся в очереди с отдельным предупреждением в отчёте.

Срок хранения деловых карточек, правовые основания удаления и архивный доступ
в исходных материалах не заданы. Автоматически удалять историю нельзя. Команда
`retention_report --actor coordinator --closed-before YYYY-MM-DD` показывает
кандидатов без удаления. После утверждения политики следует реализовать отдельный
процесс архивирования/анонимизации с legal hold и проверкой восстановленных копий.
Это остаётся явным организационным условием пилота.

Обоснование snapshot-механизма: [PostgreSQL pg_dump](https://www.postgresql.org/docs/17/app-pgdump.html)
и [экспорт snapshot](https://www.postgresql.org/docs/17/functions-admin.html).
